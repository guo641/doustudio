### P1-A: 防本地时钟回拨

**文件**: `src/doupool/license/verifier.pyx:199`

**修改**:
```python
# 新增时钟回拨检测
if last_server_sync > 0 and server_timestamp < last_server_sync:
    return "clock_rollback"
```

**语义**:
- `last_server_sync` 是上次成功心跳的服务器时间戳（写入 activated.bin）
- 本次 `server_timestamp` 必须 >= `last_server_sync`（单调递增）
- 违反 → 返回 `"clock_rollback"` 状态 → 闸门 `verify_at_import` 拒绝启动

**攻击场景**: 用户通过 NTP 同步或手动调整系统时间回到过去，试图绕过 `fresh_until` 到期检查

**防御效果**: 
- 服务器时间戳单调性保证：即使本地时钟回拨，`server_timestamp` 是服务器签名的权威时间，不受客户端控制
- 检测到回拨 → 立即拒绝，阻止利用时间回拨延长授权

**测试**: `test_clock_rollback_is_rejected_during_verification`  
模拟 `last_server_sync=1000`, `server_timestamp=999` → 状态 `clock_rollback`

### P1-B: fresh_until<=0 永不过期洞修复

**文件**: `src/doupool/license/verifier.pyx:218-221`

**修改前**:
```python
if fresh_until >= current_time:
    return "valid"
# 旧逻辑: fresh_until < current_time 直接进 grace period，没检查 <=0
```

**修改后**:
```python
if fresh_until >= current_time:
    return "valid"
# 新增: <=0 也要走 grace period 检查
if fresh_until <= 0 or (current_time - fresh_until) > _GRACE_PERIOD_SEC:
    return "expired"
return "grace_period"
```

**语义**:
- `fresh_until=0` 是 activated.bin 初始值（首次激活未心跳）
- `fresh_until<0` 理论上不应该出现（update_heartbeat_fields 有校验），但防御性处理
- 旧洞: `fresh_until=0` 时，`0 < current_time` 直接进 `grace_period` 分支，7 天内永远 valid
- 新逻辑: `fresh_until<=0` 显式检查是否超过 7 天 grace period

**攻击场景**: 
1. 激活后立即断网，`fresh_until=0`（从未心跳成功）
2. 7 天后仍可用（旧逻辑 grace_period 分支不检查 `fresh_until<=0`）

**防御效果**: 
- `fresh_until<=0` 必须在激活后 7 天内完成首次心跳，否则 `expired`
- 堵住"首次激活后永不联网"的离线滥用路径

**测试**: 
- `test_fresh_until_zero_with_expired_grace_period`: 激活 8 天后 `fresh_until=0` → `expired`
- `test_fresh_until_zero_within_grace_period_allows_temporary_use`: 激活 3 天后 `fresh_until=0` → `grace_period`（仍可用）

### P1-C: 响应 client_pubkey 回显显式校验

**文件**: `src/doupool/license/heartbeat.py:194-199`

**修改**:
```python
# 新增: 响应 client_pubkey 必须与请求一致（服务器回显校验）
response_pubkey = response.get("client_pubkey", "").lower()
if not response_pubkey:
    logger.error("响应缺失 client_pubkey 字段")
    return False, ErrCode.BAD_RESPONSE
if response_pubkey != expected_client_pubkey_hex:
    logger.error(
        "响应 client_pubkey 不匹配: expected=%s, got=%s",
        expected_client_pubkey_hex, response_pubkey
    )
    return False, ErrCode.BAD_RESPONSE
```

**语义**:
- 服务器在响应里回显客户端的 `client_pubkey`（来自请求）
- 客户端必须校验：响应里的 `client_pubkey` == 请求发送的 `client_pubkey`
- 不匹配 → 拒绝响应（`bad_response`）

**攻击场景**: 
1. MitM 攻击者替换响应的 `fresh_until` / `server_timestamp`，但忘记改 `client_pubkey`
2. 或者攻击者用不同客户端的响应重放（`client_pubkey` 不同）

**防御效果**: 
- 绑定响应与请求的身份一致性
- 服务器签名覆盖 `client_pubkey`（在 Phase-2 V4 中确认），客户端二次校验防篡改

**测试**: 
- `test_response_client_pubkey_mismatch_is_rejected`: 响应 `client_pubkey` 与预期不符 → `bad_response`
- `test_response_client_pubkey_match_passes_echo_check`: 响应 `client_pubkey` 匹配 → 通过
- `test_response_missing_client_pubkey_is_rejected`: 响应缺失 `client_pubkey` → `bad_response`
