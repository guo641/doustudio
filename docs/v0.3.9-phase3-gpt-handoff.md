## 实施细节

### P1-A: 防本地时钟回拨

**文件**: `src/doupool/license/verifier.pyx`  
**位置**: Line 199（`_check_v031_heartbeat_fields` 函数）

**代码**:
```python
# 新增: 检测服务器时间戳回拨（本地时钟篡改防护）
if last_server_sync > 0 and server_timestamp < last_server_sync:
    return "clock_rollback"
```

**逻辑**:
- `last_server_sync`: 上次成功心跳的服务器时间戳（存在 activated.bin）
- `server_timestamp`: 本次心跳服务器返回的时间戳
- **单调性要求**: `server_timestamp` 必须 >= `last_server_sync`
- 违反 → 返回 `"clock_rollback"` → 闸门 `verify_at_import` 拒绝启动

**攻击场景**:
1. 用户激活后成功心跳，`last_server_sync=1000`（Unix 时间戳）
2. 用户通过 NTP 或手动调整系统时间回到过去（如 `current_time=500`）
3. 下次心跳时 `server_timestamp=1005`（服务器时间不受客户端控制）
4. 但如果用户篡改了服务器响应（MitM），试图让 `server_timestamp=999`（< 1000）
5. **防御**: 检测到回拨 → `clock_rollback` → 拒绝启动

**测试**: `tests/test_license_p1_hardening.py::test_clock_rollback_is_rejected_during_verification`

### P1-B: fresh_until<=0 永不过期洞修复

**文件**: `src/doupool/license/verifier.pyx`  
**位置**: Line 218-221（`_check_v031_heartbeat_fields` 函数）

**代码修改前**:
```python
if fresh_until >= current_time:
    return "valid"
# 进入 grace period 分支，没检查 fresh_until <= 0
if (current_time - fresh_until) > _GRACE_PERIOD_SEC:
    return "expired"
return "grace_period"
```

**代码修改后**:
```python
if fresh_until >= current_time:
    return "valid"
# 新增: fresh_until <= 0 也要检查是否超 grace period
if fresh_until <= 0 or (current_time - fresh_until) > _GRACE_PERIOD_SEC:
    return "expired"
return "grace_period"
```

**逻辑**:
- `fresh_until=0`: activated.bin 初始值（首次激活未心跳）
- `fresh_until<0`: 理论上不应出现，但防御性处理
- **旧洞**: `fresh_until=0` 时，`0 < current_time` 永远成立 → 进 `grace_period` 分支 → 7 天内永远 `valid`
- **新逻辑**: `fresh_until<=0` 显式检查 `current_time - fresh_until` 是否超 7 天

**攻击场景**:
1. 用户激活后立即断网，`fresh_until=0`（从未心跳成功）
2. 用户在激活后第 8 天仍可使用（旧逻辑 grace_period 不检查 `<=0`）

**防御效果**:
- `fresh_until<=0` 必须在激活后 7 天内完成首次心跳
- 超过 7 天 → `expired` → 闸门拒绝启动

**测试**:
- `test_fresh_until_zero_with_expired_grace_period`: 激活 8 天后 → `expired`
- `test_fresh_until_zero_within_grace_period_allows_temporary_use`: 激活 3 天后 → `grace_period`（仍可用）

### P1-C: 响应 client_pubkey 回显显式校验

**文件**: `src/doupool/license/heartbeat.py`  
**位置**: Line 194-199（`_verify_server_response` 函数）

**代码**:
```python
# P1-C: 响应 client_pubkey 必须与请求一致（服务器回显校验）
response_pubkey = response.get("client_pubkey", "").lower()
if not response_pubkey:
    logger.error("响应缺失 client_pubkey 字段")
    return False, ErrCode.BAD_RESPONSE
if response_pubkey != expected_client_pubkey_hex:
    logger.error(
        "响应 client_pubkey 不匹配: expected=%s, got=%s",
        expected_client_pubkey_hex, response_pubkey
    )
    return False, ErrCode.BAD_RESPONSE
```

**逻辑**:
- 客户端发送心跳请求时带 `client_pubkey`（来自 activated.bin）
- 服务器在响应里回显 `client_pubkey`（已在 Phase-2 V4 确认签名覆盖）
- **客户端二次校验**: 响应的 `client_pubkey` 必须 == 请求发送的 `client_pubkey`
- 不匹配/缺失 → `bad_response` → 拒绝响应

**攻击场景**:
1. MitM 攻击者截获真实响应，篡改 `fresh_until` 延长到期时间
2. 但攻击者忘记同步修改 `client_pubkey`（或者用了别的客户端的响应）
3. **防御**: 客户端校验 `client_pubkey` 不匹配 → 拒绝

**防御分层**:
- **第一层**: 服务器签名覆盖 `client_pubkey`（Phase-2 验证）
- **第二层**: 客户端显式校验响应与请求的身份一致性（P1-C）

**测试**:
- `test_response_client_pubkey_mismatch_is_rejected`: 响应 pubkey 不匹配 → `bad_response`
- `test_response_client_pubkey_match_passes_echo_check`: 响应 pubkey 匹配 → 通过
- `test_response_missing_client_pubkey_is_rejected`: 响应缺失 pubkey → `bad_response`
