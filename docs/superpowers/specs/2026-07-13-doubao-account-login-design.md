# 豆包多账号管理器：账号登录模块设计

## 1. 目标

构建一个支持 Windows 与 macOS 的本地桌面应用。首个里程碑只实现豆包账号管理与扫码登录，为后续“视频任务列表从账号池选择可用账号执行”提供可靠的会话基础。

用户点击“添加账号”后，应用使用 Playwright 打开独立 Chromium 窗口。用户自行扫码登录，应用监听豆包网络响应，并结合用户信息、关键会话状态与页面状态确认登录成功。每个账号的浏览器数据相互隔离并仅保存在本机。

## 2. 首版范围

### 包含

- 暗色 Linear 风格桌面界面
- 账号列表、状态摘要与搜索
- 添加账号并打开豆包扫码登录窗口
- 实时展示等待扫码、验证中、成功、失败和超时状态
- 每个账号使用独立 Playwright 持久化浏览器目录
- 重新登录、启用或停用、删除账号
- 启动时及手动触发账号会话有效性检查
- SQLite 数据库与 Peewee 模型
- 文件日志、控制台日志和界面日志查看
- 敏感字段脱敏
- `run.sh`：构建 Vue 前端后通过 UV 启动 Python 桌面程序

### 不包含

- 视频任务创建与调度
- 免费额度统计
- 自动绕过验证码、风控或设备验证
- 保存账号密码
- 将会话同步到云端或其他设备

## 3. 技术路线

采用本地 FastAPI 服务、PyWebView、Vue 3、Playwright、SQLite 与 Peewee。

- Vue 3 + TypeScript + Vite：桌面界面。
- FastAPI + Uvicorn：提供本地 API、SSE 登录事件和构建后的前端静态文件。
- PyWebView：创建原生桌面窗口并打开本地服务地址。
- Playwright Chromium：打开扫码登录窗口并管理隔离会话。
- Peewee + SQLite：保存账号元数据、登录尝试和可查看日志。
- Python logging：输出滚动文件日志与控制台日志，并将适合展示的事件写入数据库。
- UV：管理 Python 依赖并启动应用。

Vue 不通过 `file://` 加载，以避免前端路由、模块资源和跨域限制。后端只绑定 `127.0.0.1`，并使用启动时生成的随机访问令牌保护本地 API。

## 4. 组件边界

### 桌面启动器

负责选择可用本地端口、生成访问令牌、启动 Uvicorn、等待健康检查通过、创建 PyWebView 窗口，并在桌面窗口退出时停止后端和登录浏览器进程。

### HTTP API

负责参数校验、数据库调用和登录流程编排，不直接包含豆包页面识别逻辑。主要接口：

- `GET /api/accounts`
- `POST /api/accounts/login-attempts`
- `GET /api/login-attempts/{id}`
- `GET /api/login-attempts/{id}/events`
- `POST /api/accounts/{id}/relogin`
- `POST /api/accounts/{id}/check`
- `PATCH /api/accounts/{id}`
- `DELETE /api/accounts/{id}`
- `GET /api/logs`
- `GET /api/health`

所有 `/api` 请求必须携带启动器注入前端页面的本地访问令牌。

### 登录编排器

每次登录尝试拥有独立状态机：

`created → launching → waiting_for_scan → verifying → succeeded | failed | cancelled | timed_out`

编排器限制同时只能存在一个交互式登录窗口，防止用户混淆扫码目标和浏览器目录。关闭浏览器视为取消；默认等待扫码超时时间为五分钟。

### 豆包登录适配器

负责：

- 打开豆包登录页。
- 监听豆包域名范围内的响应，不记录完整请求头、Cookie 或响应正文。
- 根据已确认的登录成功响应特征触发验证。
- 调用当前用户信息接口确认返回有效用户标识。
- 检查必需的会话状态与已登录页面状态，作为兼容性兜底。
- 将豆包接口路径、响应判断和用户字段映射集中在一个模块中。

登录成功不能只依赖页面跳转或某一个 Cookie。至少需要用户信息接口返回有效用户标识；网络响应和页面状态用于触发验证与诊断。豆包网页接口发生变化时，只修改适配器和对应测试夹具。

### 账号仓库

负责 Peewee 模型与事务。浏览器目录先以登录尝试 ID 创建在临时区域；登录确认后，在一个事务中创建或更新账号记录并将目录转为正式账号目录。失败或取消的临时目录会被清理。

### 日志系统

提供三个输出：终端、按大小轮转的 UTF-8 文件和数据库事件日志。统一添加时间、级别、模块、事件名、登录尝试 ID 与账号 ID。

日志过滤器必须脱敏以下内容：Cookie、Set-Cookie、Authorization、访问令牌、手机号、二维码内容、完整响应正文和本地浏览器目录中的敏感文件内容。

## 5. 数据模型

### Account

- `id`: UUID 字符串，主键
- `display_name`: 本地显示名
- `doubao_user_id`: 豆包用户标识，唯一且可空
- `doubao_nickname`: 豆包昵称，可空
- `profile_dir`: 相对于应用数据根目录的浏览器目录
- `status`: `active | expired | disabled | error`
- `enabled`: 是否允许后续参与调度
- `last_verified_at`: 最近成功验证时间
- `last_error`: 脱敏后的最近错误摘要
- `created_at`, `updated_at`

### LoginAttempt

- `id`: UUID 字符串，主键
- `account_id`: 重新登录时关联账号，可空
- `state`: 登录状态机状态
- `error_code`, `error_message`: 脱敏后的失败信息
- `started_at`, `finished_at`

### AppLog

- `id`: 自增主键
- `level`, `module`, `event`
- `message`: 脱敏后的可读信息
- `account_id`, `login_attempt_id`: 可空
- `created_at`

SQLite 启用 WAL、外键约束和 busy timeout。数据库迁移以版本表和顺序迁移函数管理，不在生产启动时直接依赖 `create_tables(safe=True)` 演进结构。

## 6. 登录数据流

1. 用户点击“添加账号”。
2. Vue 创建登录尝试并订阅该尝试的 SSE。
3. 后端创建临时持久化浏览器目录，启动有界面的 Playwright Chromium。
4. Chromium 打开豆包，用户自行扫码并处理可能出现的验证。
5. 适配器从相关登录响应触发 `verifying`，随后验证当前用户接口与会话状态。
6. 验证成功后，仓库在事务中保存账号记录并固定浏览器目录。
7. 后端推送 `succeeded` 事件，Vue 刷新账号列表；登录浏览器正常关闭。
8. 失败、超时或用户关闭窗口时，推送对应状态并清理临时目录。

同一个豆包用户再次添加时不创建重复账号，而是提示用户选择更新既有账号会话。首版默认保留旧会话，只有用户确认重新登录后才替换正式浏览器目录。

## 7. 界面设计

采用已确认的暗色 Linear 紧凑型界面：

- 左侧栏：账号池、视频任务占位入口、生成结果占位入口、运行日志、设置。
- 顶部状态：当前页面与本地服务状态。
- 账号页：账号总数、可用数量、今日额度占位卡片，以及账号列表。
- 添加账号弹层：启动提示、扫码等待状态、登录验证进度和失败重试。
- 状态颜色：绿色表示有效，黄色表示需操作，红色表示错误，灰色表示停用。

视频任务和额度功能在首版只显示“即将支持”或不展示可操作控件，避免产生已实现的误解。

## 8. 错误处理

- Chromium 未安装：返回明确错误，并提示运行 Playwright 安装步骤。
- 浏览器启动失败：登录尝试进入 `failed`，保留脱敏错误。
- 扫码超时：进入 `timed_out`，允许重新发起。
- 用户关闭窗口：进入 `cancelled`。
- 登录接口变化：验证失败并记录响应路径和状态码，不记录正文或凭证。
- 数据库忙：使用 busy timeout 和有限重试；仍失败时向界面返回可操作错误。
- 应用异常退出：下次启动将遗留的进行中尝试标记为失败，并清理对应临时目录。
- 网络断开：保持登录窗口并显示等待网络恢复；超过总超时时间后失败。

## 9. 安全边界

- 只用于用户本人或团队明确授权的账号。
- 用户自行扫码、处理验证码和设备确认。
- 不绕过平台限制、免费额度或风控。
- 不保存密码。
- 浏览器会话目录不进入 Git，权限限制为当前系统用户。
- 删除账号时必须二次确认；确认后删除数据库记录与对应本地会话目录。
- 后端只监听回环地址，本地 API 使用随机令牌。

## 11. 启动流程

`run.sh` 在 macOS、Linux 和 Git Bash 环境执行以下步骤：

1. 检查 `uv`、Node.js 与 npm。
2. 在 `frontend` 中安装锁定依赖并执行生产构建。
3. 执行 `uv sync`。
4. 检查 Playwright Chromium；首次缺失时执行安装。
5. 执行 `uv run python -m doupool.main`。

Windows 原生环境后续提供等价的 `run.ps1`；本里程碑按用户要求先交付 `run.sh`。

## 12. 测试与验收

### 自动测试

- Peewee 模型、迁移和事务测试。
- 登录状态机的成功、失败、取消、超时与恢复测试。
- 豆包适配器使用脱敏网络夹具测试响应识别和用户信息映射。
- 日志脱敏测试，确保敏感字段不会进入文件或数据库。
- API 参数、令牌校验、SSE 事件与错误码测试。
- Vue 组件状态测试与生产构建测试。
- 后端健康检查和静态文件服务冒烟测试。

真实豆包扫码登录作为人工验收，不在 CI 中保存真实账号会话。

### 验收标准

- 执行 `run.sh` 后先完成前端构建，再启动桌面窗口。
- 点击“添加账号”能打开独立 Chromium 豆包登录窗口。
- 扫码成功后，应用在十秒内识别登录并新增账号。
- 关闭并重新启动应用后，账号仍存在且会话可以验证。
- 两个账号的浏览器目录相互隔离。
- 登录失败、取消和超时均有明确界面状态与脱敏日志。
- 数据库和日志中不存在密码、Cookie、Authorization 或二维码内容。
